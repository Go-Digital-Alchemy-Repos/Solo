PHASE 1 — DATABASE: EXTENSIONS + INDEXES + SEARCH VECTORS
------------------------------------------------------------

1) Enable Postgres extensions (migration-safe)
- Enable pg_trgm (for fuzzy user search)
- Enable unaccent (optional but recommended for better matching)

2) Users search fields
Goal: fast prefix + fuzzy search for usernames.
- Ensure users has:
  - username (text) and optionally displayName (text) and bio (text)
- Add a generated searchable “usernameNormalized” or use lower(username)
- Add indexes:
  - GIN index on username using gin_trgm_ops
  - If displayName exists, add gin_trgm_ops index
  - If searching bio, add gin_trgm_ops index (optional; consider performance)

3) Solos full-text search (title/tags/transcript)
We want full-text search across:
- title
- tags (string array or json; normalize to a text field for FTS)
- transcript text (derive from transcript JSON)

Add to solos table (additive):
- searchText (text) nullable
- searchVector (tsvector) nullable

Rules:
- searchText should be a concatenation of title + tags + transcriptPlainText
- searchVector should be to_tsvector('english', unaccent(searchText))
- Add a GIN index on searchVector

Implementation options:
A) Triggers (Postgres) to maintain searchVector automatically
B) Maintain searchText/searchVector in application code whenever a solo is created/updated/transcribed
Choose the simplest non-destructive approach:
- If Drizzle migrations support SQL triggers comfortably, prefer trigger (less app code).
- Otherwise, implement in server code with a single helper to update the search fields, called:
  - after solo creation
  - after transcription completes
  - after title/tags updates

Add indexes:
- GIN (searchVector)
- B-tree (createdAt desc) for paging search results

PHASE 2 — BACKEND: SEARCH API (Express) + QUERY OPTIMIZATION
------------------------------------------------------------

Create server/routes/search.routes.ts mounted at:
- /api/search

Use existing validateBody/validateQuery and AppError pattern.
Ensure all endpoints are authenticated or public depending on product intent:
- User search likely should be authenticated to reduce scraping.
- Solos search can be public or authenticated; follow existing app behavior.

Endpoints:

1) GET /api/search/users?q=&cursor=&limit=
Behavior:
- q required, min length 1–2
- Return users matching username/displayName/bio using trigram similarity and prefix match.
- Sort:
  - exact username match first
  - prefix matches next
  - then similarity score desc
- Cursor pagination:
  - return { items, nextCursor }
  - cursor can encode lastScore + lastId or lastUsername; keep deterministic ordering.
Return shape:
{ ok: true, data: { items: [{ id, username, avatarUrl, bio? }], nextCursor } }

2) GET /api/search/solos?q=&cursor=&limit=
Behavior:
- Use FTS:
  - plainto_tsquery or websearch_to_tsquery if available
  - rank with ts_rank_cd
- Search across searchVector
- Return solos with:
  - id, title, tags, duration, audioUrl, createdAt
  - author summary (id, username, avatarUrl)
  - optional snippet/highlight:
    - return a short excerpt from searchText (do not return full transcript)
- Sort by rank desc then createdAt desc for tie-breaker
- Cursor pagination:
  - encode lastRank + createdAt + id

3) GET /api/search/suggestions?q=&limit=
Behavior:
- Return mixed suggestions:
  - top users by prefix
  - top tags by frequency (if tags exist)
  - optionally recent trending search terms (future)
This powers typeahead.

4) OPTIONAL: GET /api/search/recent
- Return the current user’s recent searches (stored in DB)
- If not implemented, implement local-only recent searches in client.

Performance requirements:
- Add server-side limits (default 20, max 50)
- Add rate limit for search endpoints (to prevent scraping and runaway usage)
- Ensure queries use indexes (EXPLAIN is optional; confirm logically)
